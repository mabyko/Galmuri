# Galmuri project workflow

- Read `TASKS.md` and the relevant specifications before implementation. `TASKS.md` is the single source of truth for progress; `docs/roadmap.md` explains sequencing.
- Mark the task being worked on `IN PROGRESS`. Keep at most one task active in the shared tracker. Record blockers on the task rather than marking it complete.
- When completing work, update its checkbox, current focus, next task, and relevant validation evidence in the same change. Mark only work actually implemented and checked as complete.
- Keep product requirements in `docs/product-plan.md`, technical gates in `docs/technical-validation.md`, substantive architecture decisions in `docs/adr/`, and completed checks in `docs/validation.md`.
- English is the canonical documentation language. Keep the four READMEs aligned when their shared content changes. Dated Korean planning references are not automatically synchronized translations.
- Keep real browser profiles, bookmarks, backups, credentials, private URLs, and local agent/runtime state out of public source and fixtures. Use synthetic data and dedicated test profiles.
- A prototype interaction or catalog compilation is not evidence of native app, Chrome write, synchronization, or runtime locale support.
- After development/testing, use `macos-release-reinstall` to install and verify the current local Release for maintainer review, then `macos-dev-app-cleanup` to remove only proven development/test app bundles, exact-path processes, and registrations. Preserve all app data, settings, and permission records. Do not leave a development app as the review installation.
- Follow `apple-bundle-id-guardrails` for identity/signing changes and `apple-app-icon-generator` for primary icon changes. Resolve the SwiftPM packaging identities from `Config/BuildIdentities.json`; keep Debug/Release IDs, data domains, names, and icons separate. No Apple team registration or public publication is implied.

- Permission guidance may open the Settings pane once per user click (or Settings itself if the URL is rejected) and show written steps. Galmuri product code must not inspect or operate another app’s UI for browser connection or permission guidance: no Accessibility client calls/trust requests, Apple Events/AppleScript, screen capture, posted input, or control of another app’s focus/activation. Do not request Accessibility or Automation permission for this purpose, even for a single bounded attempt. QA must not script System Settings or reproduce the reported click without a new explicit maintainer request. This does not prohibit Galmuri’s own accessibility labels/traits, VoiceOver/keyboard support, own windows/activation, ordinary in-app tasks/loops, native file panels, browser process-state checks, or Debug-only capture of its own UI. The mechanism is rejected as a product boundary, not established as the incident’s cause. See [ADR 0008](docs/adr/0008-optional-accessibility-settings-navigation.md).
