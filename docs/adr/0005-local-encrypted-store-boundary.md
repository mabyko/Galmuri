# 0005 — Local encrypted-store adapter boundary

Historical bounded experiment accepted 2026-10-24. **Further implementation deferred by the maintainer on 2026-10-25.** The native app exposes only a disabled “Planned” item in Settings → Labs, with no activation preference or Keychain access. The disconnected core experiment's source was removed on 2026-11-12 (local recovery copy: `build/removed-encrypted-store-2026-11-12.tar.gz`); its recorded findings and the conditions below are retained as historical design evidence, not active implementation work.

Chromium tag `153.0.8010.52` resolves to commit `78e5e45d4bb41035e17ea4da2cc257f496416ac9`. Its macOS key provider uses a `v10` AES-128-CBC envelope, PBKDF2-HMAC-SHA1 with the browser's existing password, and fixed parameters. Implement that compatibility path with system CommonCrypto; do not create a different encryption format or infer key material from file paths. Context7 had no CommonCrypto coverage; the installed Apple SDK headers and pinned Chromium implementation establish the API/format details.

The cipher accepts explicit password bytes in memory and never reads, creates, changes or persists Keychain credentials. An unavailable/wrong key, unknown envelope, divergent copies, account stores or nonempty merged ordering must not trigger a guessed fallback. CBC is not authenticated encryption: canonical encoding, JSON/codec checks and source identities are separate validation layers. Real browser credential access needs a later explicit native authorization flow, cancellation/error behavior and a supported browser identity.

For observed local stores, support only `Bookmarks`, `EncryptedBookmarks2` and an optional empty-object `BookmarkMergedSurfaceOrdering`. When clear/encrypted copies coexist, require identical decoded **bytes**, matching the pinned loader's comparison, rather than guessing the runtime encryption stage from defaults or filenames. Preserve original bytes and file presence on no-op, and preserve verified identities/metadata/order on edits. Encrypted-only output must not introduce a plaintext copy. Unknown/account/custom-ordering combinations remain blocked.

A group transaction must bind review to the entire source set, identities, dependencies and absence/presence. Back up the full set, stage verified replacements and a durable journal, recheck before replacements, and retain evidence after interruption. Recovery must recognize original/staged states and reject newer/unrecognized writers; restore must back up the current set. Multiple renames are not atomic. The bounded test coordinator requires an app-owned root and a controlled no-launch interval; it cannot promise crash/restart safety for an arbitrary live Chrome profile.

Use the already authorized synthetic Chrome for Testing profile, its verified mock-keychain provenance and a separate DevTools connection for adoption/restore evidence. A temporary QA observer may read the browser model in that disposable profile; it is not a product dependency. No encryption feature override, real-user profile/Keychain read, forced browser exit or public publication is implied.

External connected-profile writes remain disabled. Enabling them requires real credential authorization and native review/history integration, validated file-set recovery/lifecycle handling, version/account scope and actual adoption/restore evidence. A synthetic mock-keychain proof alone does not close those gates.
