# Galmuri 제품 기획서

상태: 기획 초안 v0.1 · 2026-10-23. 사용자 합의와 구현 제안을 구분한다. 이번 산출물은 문서와 인터랙티브 디자인 시안이다.

## 제품과 사용자 문제

개인·업무 Chrome 프로필에 흩어진 북마크를 브라우저마다 오가며 정리해야 한다. 내보내기 파일을 편집해서 다시 가져오면 지속적인 관리와 변경 추적이 어렵다. Galmuri는 연결한 프로필의 북마크를 앱 작업본으로 가져와 정리하고, Chrome에서 그동안 바뀐 내용까지 병합해 원래 프로필에 반영하는 Mac 앱이다.

이름은 **Galmuri · 갈무리**. 설명 문구는 “여러 프로필의 북마크를 한곳에서 다듬고, 브라우저에 반영하세요.” 상표·유사 제품명 조사는 아직 하지 않았다.

## 확정 요구와 설계 가정

| 구분 | 내용 |
| --- | --- |
| 사용자 확정 | 독립형 macOS 앱, **SwiftUI 네이티브 UI**, Chrome 우선, 프로필마다 확장 설치 불필요 |
| 사용자 확정 | 가져오기 이후 지속적으로 편집·반영. HTML 내보내기만으로 대체하지 않음 |
| 사용자 확정 | 최초 Base, 앱 작업본 Ours, 저장 직전 원본 Theirs의 3-way merge |
| 사용자 확정 | 편집 중 Chrome 사용 가능. 저장 시 완전 종료 확인, 충돌 해결, 변경 검토, 백업·복원 |
| 사용자 확정 | 기존 Notion 스타일 다크 UI의 차분함, 폴더 탐색·목록 중심 편집을 계승 |
| 구현 제안 | 한 번의 저장은 하나의 프로필에 한정. 여러 프로필의 변경은 독립적으로 보관 |
| 구현 제안 | 첫 지원 대상은 검증된 평문 로컬 저장 형식. 읽기와 쓰기 지원 수준을 각각 표시 |
| 미정 | 최소 macOS 버전, 배포·서명·App Sandbox 방식, 지원 Chrome 버전과 계정 저장소 범위 |
| 미정 | Ego 직접 읽기/쓰기. Chrome과 같은 형식이라고 가정하지 않음 |

지원 형식이 검증되지 않은 프로필은 연결 정보와 불가 사유를 보여주되 쓰기는 비활성화한다. **이 상태는 제품 MVP 완료가 아니다.** 직접 반영을 안전하게 지원할 수 없다면 범위를 다시 논의한다.

## MVP 범위

1. **프로필 연결:** 사용자가 선택한 Chrome 데이터 폴더에서 프로필 발견, 표시 이름·경로·저장소·권한·읽기/쓰기 지원 상태 확인. 같은 표시 이름도 경로로 구분. 연결 해제는 Chrome 원본을 삭제하지 않는다.
2. **지속적인 작업본:** 프로필마다 Base와 Ours를 앱 내부에 저장하고 앱 재실행 뒤 복원. Chrome과 다르게 바뀐 항목을 별도로 표시한다. JSON 백업은 작업본 내보내기 수단이며 원본 전체 복원용 백업과 구분한다.
3. **편집:** 중첩 폴더 생성·이름 변경·이동, 북마크 추가·이름/URL 변경, 다중 선택 이동, 드래그앤드롭 및 메뉴 대안, 검색, 동일 URL 보기, 제외·되돌리기. 중복은 자동 삭제하지 않는다. ‘제외’는 작업본에서 제외한 뒤 반영 검토에 삭제로 표시한다.
4. **원래 프로필에 반영:** 종료 확인 → 최신 원본 재조회 → 3-way merge → 충돌 해결 → 변경 검토 → 원본 백업 → 재확인 → 안전한 저장. 검증된 프로필에서 실제 반영까지 제공한다.
5. **백업과 복구:** 반영 이력, 프로필별 백업 위치·시점·검증 상태, 복원 전 차이 검토. 실패·앱 중단 시 복구 가능한 상태 유지.
6. **호환 내보내기:** 전체/폴더 하위 Netscape HTML과 작업 JSON 백업·불러오기. 가져온 HTML은 Chrome 식별자와 연결되지 않은 별도 작업본으로 다룬다.

계정 로그인, 클라우드 동기화 서비스, AI 분류, 링크 방문·미리보기 수집, 깨진 링크 크롤러, 확장 프로그램, Windows, 프로필 간 원본 이동의 일괄 트랜잭션은 이번 MVP에서 제외한다. 프로필 간 복사는 후속 기능으로 두고, 초기에는 프로필 안의 정리를 완성한다.

## 화면과 사용 흐름

### 1. 처음 연결

빈 화면에서 ‘Chrome 프로필 연결’을 선택한다. 필요한 폴더와 읽기 목적을 설명한 뒤 macOS 폴더 선택창을 연다. 선택한 폴더에서 발견된 프로필을 보여주고 연결 대상을 고른다. 사용자가 취소하면 빈 화면으로 돌아간다.

초기 환경 조사에서 Chrome 데이터 폴더 접근은 `Operation not permitted`로 실패했다. 앱이 선택창을 띄우면 반드시 해결된다고 약속하지 않는다. 거부되면 “이 폴더를 읽을 수 없어요. 폴더를 다시 선택하거나 macOS 접근 권한을 확인하세요.”와 재선택·도움말을 제공하고 우회하지 않는다. 처음부터 모든 파일 접근 권한을 요구하지 않는다.

### 2. 편집

왼쪽에 프로필과 폴더, 가운데에 검색 가능한 북마크 표, 필요할 때 오른쪽에 선택 항목 편집 패널을 둔다. 프로필을 바꾸면 해당 작업본으로 전환한다. ‘앱에 보관됨 · Chrome 반영 전’ 상태를 항상 구분한다. 앱 자동 저장은 Chrome 반영을 의미하지 않는다.

상단 주 동작은 ‘변경사항 검토’. 변경이 없으면 비활성화한다. ‘변경사항’ 보기에서는 이름/URL/폴더/순서 변경과 삭제 예정 항목을 확인하고 개별로 되돌릴 수 있다. 원본 프로필이 사라져도 작업본을 보존하며 재연결할 수 있다.

### 3. 저장 전 Chrome 확인

반영 대상 프로필과 앱 변경 건수를 표시한다. Chrome이 실행 중이면 “최신 북마크를 확인하려면 Chrome을 종료해 주세요. 열린 작업을 마무리한 뒤 다시 확인하세요.”를 보여준다. ‘편집으로 돌아가기’와 ‘종료 상태 다시 확인’을 제공한다. 강제 종료하지 않고, 창이 닫혔다고 종료로 간주하지 않는다.

프로필이 같은 Chrome 프로세스를 공유할 수 있으므로 다른 창에도 영향이 있음을 알린다. 백그라운드 프로세스·사용자 데이터 경로·재실행을 확인할 수 없으면 반영을 막는다.

### 4. 최신 변경 확인과 충돌 해결

Chrome 종료 뒤 Theirs를 읽는다. ‘Chrome에서 새로 생긴 항목’, ‘앱 변경’, ‘자동으로 합칠 내용’, ‘선택이 필요한 내용’을 분리한다. 개발 용어 Base/Ours/Theirs 대신 ‘처음 가져왔을 때 / 앱에서 수정 / Chrome에서 수정’을 화면에 쓴다.

동일 필드의 다른 값, 삭제 대 수정, 다른 폴더로 이동, 서로 양립하지 않는 정렬은 사용자 선택을 요구한다. 충돌마다 항목 이름·출처·전체 경로·세 값과 선택 결과를 보여준다. 기본값을 미리 선택하지 않는다. 미해결 충돌이 있으면 진행할 수 없다. 폴더 삭제는 하위 항목 변경까지 포함해 판단한다.

### 5. 최종 검토와 반영

추가·수정·이동·순서 변경·삭제를 항목별로 보여주고, Chrome 변경의 유지 여부와 삭제될 하위 항목을 명시한다. 자동 병합 내용도 검토 가능해야 한다. 사용자가 본 결과에 대한 승인 이후 원본 백업을 만들고 검증한다. 직전 원본·실행 상태가 달라졌다면 승인을 무효화하고 재병합한다.

버튼은 ‘백업 후 Chrome에 반영’. 백업 실패, 권한 철회, 디스크 부족, 검증 실패에서는 교체하지 않는다. 파일 교체 성공 뒤에는 ‘파일 반영 확인됨 / Chrome 재시작 확인 대기 / 동기화 확인 대기’를 구분한다. 정상 반영된 파일을 새 Base로 삼고, 재시작 뒤의 추가 변경은 새 원본으로 비교한다.

### 6. 백업과 복원

원본 백업은 프로필·저장소·앱 버전·Chrome 버전·시점·파일 해시와 함께 관리한다. 앱 작업본 백업과 다르게 정확한 원본 복구를 목적으로 한다. 첫 버전은 사용자가 지우기 전까지 보관하는 안을 제안한다.

복원도 Chrome 종료 확인, 현재 상태 백업, 차이 검토, 변경 재확인, 안전한 교체를 거친다. 백업 이후 새로 생긴 북마크가 사라질 수 있음을 구체적인 차이로 알린다. 서버 동기화 내용까지 되돌리는 기능이라고 설명하지 않는다. 실패하면 원래 상태와 복구 안내를 유지한다.

## 현재 산출물과 다음 결정

현재는 합성 데이터로 편집·저장 검토·충돌 해결·복원 화면을 검토한다. 실제 프로필 접근과 Chrome 반영을 수행하지 않는다. 화면 시안은 네이티브 앱의 구성과 문구를 검토하기 위한 HTML 자료이며 WebView 채택을 뜻하지 않는다.

다음 구현은 권한·프로필 발견 검증부터 시작하는 안을 제안한다. 쓰기 가능성, 최소 macOS 버전, 배포 형태를 확인한 후 SwiftUI 앱의 세부 구조와 지원 조합을 확정한다. 실제 사용자 원본 반영은 검토 가능한 차이와 검증된 복원 수단이 준비된 이후 다룬다.
