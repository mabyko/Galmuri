# Chrome API working copies and reviewed editing

Experimental checkpoint · Release29 · 2026-10-29. The existing file editor remains available. Choose **Settings → Labs → API connections and editor** for the separate API workflow. Extension instructions and a matched ZIP are in Labs; see [installation and experimental limits](labs.md). The ordinary File-menu API entry and its shortcut are removed.

Release27 fixes the earlier progress/result sizing blocker and adds acknowledged stop, API multi-selection/drag/navigation and a restrained gray/blue appearance. [Refinement details and measured limits](native-refinement.md) explain the changes. Normal real-profile writes remain disabled; matching extension/helper protocol2 is required.

## Connect and read

Install the matching local extension/native host in an approved dedicated environment using the [bridge setup guide](chrome-bridge-proof.md). Its permissions are now `bookmarks`, `nativeMessaging` and `storage`; there are no content scripts or website host permissions. Keep its connection tab open, label the profile, approve the matching code in Galmuri, and check approval in the extension. Then reload connections in the API workspace and select a browser folder as the scope of a persistent working copy.

The snapshot reads the running browser's API-visible names, URLs, tree order, IDs and capability flags across all exposed roots. It does not decrypt or edit Chrome files and does not request Keychain access. Account/managed folders remain available for local reading where Chrome exposes them, with browser writes blocked. Each selected folder scope has its own working copy; equal URLs and same-type permanent roots are not merged by name. Reinstallation/cloned installation IDs or ambiguous simultaneous sessions require explicit reconnection rather than guessed routing.

Sessions expire after five minutes or disconnect when the extension tab closes. Work survives app/browser restart; a new session must be approved. Connection refresh never silently replaces saved edits. The API sidecar has its own version/revision; existing `workspace.json` v1 is neither migrated nor replaced. Stale parallel windows fail their revision check instead of overwriting newer work.

## Edit, review and refresh

Create/edit bookmarks and folders, navigate with Back/Forward/Up, select multiple items, drag/move/delete within the same working profile, reorder individual items, search and undo local edits. Saved edits remain after relaunch; session Undo does not. Discard local changes previews the current-to-Base diff. Folder deletion previews its descendants and only changes the working copy initially. HTML export uses the open folder's children or the whole selected working scope, independently of search/selection. Chrome HTML import remains additive; it does not replay deletions or update old IDs.

Review requests a fresh browser snapshot and merges Base/Ours/Theirs. Choices begin unresolved, show all three values, and reset acknowledgement when changed. **Save merged working copy only** archives old work and advances the local baseline after a second source check. **Apply to paired Chrome** requires acknowledgement and a writable dedicated session. Chrome stays open; never use the file backend's quit/replace flow for API operations.

The apply targets existing API IDs, creates missing parents/items, performs same-store moves and updates, then reconciles sibling order. Read-only fields/dates do not become edits or false metadata conflicts. A full semantic fingerprint and relevant capability/hierarchy checks invalidate stale plans. Each call has small sequential durable intent and observed-result records; unexpected concurrent changes stop the remaining batch. These checks cannot provide a browser-wide lock or remove the final read/write race.

## Recoverable removal and restore

Applying a removal moves originals into a visible **Galmuri Recovery <job prefix>** folder inside the selected scope. Its exact API ID is tracked; similarly named user folders are never hidden by name. Keep recovery folders until their contents are no longer needed. They are excluded from that working copy's ordinary tree, while remaining visible in Chrome and the full API snapshot.

**Review undo of last apply** compares the last after-state, its before-state and current Chrome state. Conflicts require new choices/approval; original IDs are moved back where they still exist. Recreated or permanently removed browser nodes, changed recovery-folder identity, account migration and new management restrictions block unsupported restoration. This is not a lossless original-file backup or account-wide undo.

On an exception or missing response, some calls may have succeeded. The saved pending job blocks another apply, including after app restart. **Review interrupted apply** previews adopting the current browser state; explicit confirmation archives the local working copy, verifies the same snapshot, clears the extension's interrupted-operation marker and advances Base/Ours locally. It does not undo browser changes. An apply's `.before`, `.source`, `.job`, `.operation-N.intent`, `.operation-N.observed`, `.stop`, `.stop-ack` and `.result` records are deleted after a successful apply or adoption, and snapshot/adopt job files are deleted when the request returns; the records of an interrupted apply stay until adoption, and `.archive`/`.interrupted` recovery copies are kept. All of them are private under the API data directory; do not publish them. Because the host withholds an apply when under 90 seconds of the pairing session remain, the app refuses to start an apply with under 120 seconds left, before writing any record or pending job; reconnect in Chrome and review again.

Closing/disconnecting the extension stops future intent exchanges; the host also checks the exact owning app process before each new mutation intent. An in-flight call may still complete. The workbench offers **Stop after current call**; closing it or cancelling/timing out an apply also writes a stop request. The host acknowledges it before another mutation intent, the extension refreshes and reports stopped, and pending work remains for explicit review. A call already started or acknowledged can finish; a late stop may follow success. New operation records retain sequential intents/observations; historical protocol1 progress files held only the latest state. No automatic replay, rollback or foreground/UI manipulation is attempted. Remote sync is a separate browser/account behavior and is not verified here.

## Explicit test-write gate

Ordinary native-host connections are read-only. The previous pairing-only marker does **not** enable writes. Dedicated API write testing additionally requires regular, owner-only `.galmuri-api-write` files in **both** the task-owned Chrome root and Galmuri workspace, containing exactly `Galmuri dedicated API write proof v1` plus newline. Pass `--enable-api-test-writes` to `scripts/setup-bridge-proof.py`; the resulting task-only launcher supplies `--api-test-writes` to the host. The host independently validates the workspace marker. No app toggle enables this for real/shared profiles.

Do not register test launchers in actual Chrome roots, remove recovery folders during a test, relax privacy controls, or use real data as fixtures. Existing Debug/Release identities and icons remain separate. User Chrome host-registration/TCC UX, real-profile write authorization, account/cross-store writes, permanent deletion, complete physical keyboard/VoiceOver review, large-data stress and broader failure/sync combinations remain outside this checkpoint.

## Local validation

Swift tests cover opaque IDs, duplicate URLs, tree/schema/capability guards, revision conflicts, existing-workspace preservation and stale editors. Node tests cover actual API operation planning through a synthetic API, unexpected concurrent changes, lost replies, persistence failure before mutation and multi-chunk mixed-script transport. Dedicated CFT runs exercise the signed native app/host and the same extension client/API modules, including real model changes, semantic restore, lost-response injection, explicit adoption and normal browser restart. A QA-only extension worker drives those calls; physical toolbar/tab/button interactions are not inferred from it. See [TASKS](../TASKS.md) and [completed evidence](validation.md).
